# Model Council Synthesis — Cascade Listening-Time Architecture

**Consulted:** Claude Opus 4.8, Gemini 3.1 Pro, GPT-5.5 — Deep Dive depth.

All three models converged on the same fundamental shape: keep `cascade-core` pure, accrue audible time on the existing `Tick` path, use a **G-Counter CRDT** (per-device monotonic counters merged via `max` and summed across devices), back the service with **Rust + Axum + SQLx + Postgres** on a subdomain, and authenticate with **email magic-link**. Where they differ is in *granularity of measurement gating*, *whether the core emits sync triggers*, *threshold tuning*, and *what to do about pre-existing privacy promises and tick-loop battery cost*.

## 2. Where Models Disagree

| Topic | Claude Opus 4.8 | Gemini 3.1 Pro | GPT-5.5 | Why They Differ |
|---|---|---|---|---|
| **What gates accrual** | `intent.is_playing() && !muted` (intent-only) | `intent.is_playing() && !muted && tracking_enabled` (intent-only) | `tracking_enabled && audio_confirmed_playing` — introduces a new `audio_confirmed_playing` flag flipped by `PlatformPlaybackStarted`/`Paused`/`Error` | GPT-5.5 dug deepest into the existing reducer and found that `Play` sets intent immediately but `PlatformPlaybackStarted` is the only signal audio actually began. Opus/Gemini trust intent; GPT-5.5 distrusts it because of autoplay-blocked browsers. |
| **Does core emit a sync trigger?** | Yes — adds `Effect::RequestSync { device_total_ms }` when flush threshold crosses | No explicit sync effect; shell observes `unflushed_ms` | No — shells observe `snapshot.listening.unsyncedMs` and decide cadence themselves | Opus prefers an explicit core signal so cadence policy is centralized; GPT-5.5 argues sync cadence is platform-specific (lifecycle, reachability, auth) and shouldn't pollute core |
| **Flush threshold** | 60 s (`FLUSH_THRESHOLD_MS = 60_000`) | 60 s | 5 s local persist + 30 s unsynced before network sync | Opus optimizes for low write churn; GPT-5.5 optimizes for crash-loss minimization (5 s local writes), separating local persistence cadence from network sync cadence |
| **What sync wire format carries** | Absolute `device_total_ms` + `client_seq` idempotency key | Absolute `local_lifetime_ms` only | Absolute `deviceTotalMs` + `ledgerVersion` | Opus adds a per-request monotonic counter as a belt-and-suspenders replay guard; Gemini relies on `GREATEST` alone; GPT-5.5 versions the ledger schema |
| **Tick-loop scope change** | Mentioned (widen gate to `isTimerActive \|\| isPlaying`) but treated as routine | Not explicitly addressed | Flagged as a top-3 risk — proposes 1 s ticks for accrual while keeping 250 ms for timers, to limit battery cost | GPT-5.5 traced the tick-loop code on all four shells (web, Android, Apple, Windows) and noticed they only tick during timers today, so untimed listening introduces a *new* always-on 250 ms loop |
| **Token format** | JWT-style session ("session_jwt") | Long-lived JWT after magic-link | **Opaque server-side tokens** (not JWT) | GPT-5.5 specifically argues opaque tokens because they make account deletion, logout-all-devices, and revocation trivial on a single Postgres VPS; Opus/Gemini default to JWTs without addressing revocation |
| **Acknowledging synced time** | `Command::ApplySyncedTotal { merged_total_ms }` (display only; never lowers local slot) | `Command::AcknowledgeTrackedTime { ms_flushed }` (drops from unflushed accumulator) | `Command::ListeningSyncSucceeded { synced_device_total_ms, server_aggregate_total_ms }` | Gemini's model is "deltas + ack"; Opus and GPT-5.5 both go full G-Counter (absolute slot, no decrement). Gemini's design is actually slightly inconsistent — it claims monotonic counters but then asks the shell to subtract synced amounts locally. |
| **Deletion epoch / device-id rotation** | Periodic sweep of orphan unlinked devices | Cascade `DELETE` only | **Rotates `device_id` on "delete listening data"** so a stale offline PUT can't resurrect deleted totals | GPT-5.5 surfaced a subtle attack/bug: with grow-only counters, a forgotten offline device could later push a stale higher counter and undo a deletion. Opus/Gemini missed this. |
| **Privacy posture change** | Treated as a default-on benign feature; recommends first-run disclosure | Brief mention; recommends a Settings toggle | **Flagged as a hard launch blocker** — found Cascade's existing privacy page promises "no accounts, no analytics, no servers receiving data about users" and says the privacy copy must ship in the same release artifact as the feature | GPT-5.5 actually read `apps/web/public/privacy/index.html`. Opus/Gemini didn't surface this conflict at all. |

|---|---|---|
| Claude Opus 4.8 | The `RestoreListening` handler should adopt `max(in-memory, restored)` so partially-written blobs on best-effort writers (Windows/macOS) can never *lower* the in-memory slot | Cheap monotonicity guard that prevents a corrupted local file from regressing a user's lifetime total. | Gemini 3.1 Pro | Background sync restrictions on iOS/Android mean `FlushTrackedTime` must persist *synchronously* to local disk before the app is suspended; network sync can wait | Important lifecycle concern Opus/GPT-5.5 underweight — if the OS kills the app between accrual and persistence, the un-persisted minute is lost forever. |

## 4. Comprehensive Analysis

### High-Confidence Findings

Three independent reads of the Cascade codebase converged on the same architecture, which is the strongest possible signal that it's correct. **All three models agree the feature must be a pure accumulator inside the existing reducer, accruing on `Tick` only when audio is genuinely playing, with the device acting as a G-Counter replica and the server doing nothing more sophisticated than `GREATEST` on upsert and `SUM` on read.** Claude Opus 4.8 grounds this most explicitly in the Clave kata's invariants — the reducer already sees play state and mute on every tick, so measurement adds *zero* new core dependencies — but Gemini 3.1 Pro and GPT-5.5 reach the same destination by independent paths. The unanimous rejection of last-write-wins is similarly strong: all three walk through the same concurrent-offline scenario (Device A logs 2 h, Device B logs 1 h, LWW silently destroys one of them) and reach the same conclusion that grow-only counters are the only correct primitive when "the whole point is that concurrent listening must add, not overwrite."

The backend recommendation is even more tightly converged. **Rust + Axum + SQLx + Postgres on a subdomain behind Apache, with systemd, magic-link auth, three-or-four tables, and four-to-seven JSON endpoints** is the shape every model independently arrived at. The convergence on magic-link over OAuth and passkeys is particularly notable because each model evaluated the same three alternatives against the same criteria — minimal third-party dependency, cross-platform link handling, PII minimization, payoff for an opt-in counter — and all three reached the same verdict that passkeys are the long-term right answer but premature for v1 and OAuth is disproportionate. When three frontier models with different training corpora and reasoning styles agree this completely on architecture, the residual uncertainty is in implementation detail, not direction.

Local persistence and build ordering also produced near-identical answers. All three name the same per-platform storage sinks (localStorage on web, DataStore on Android, Application Support on Apple, LocalAppData on Windows), all three flag watchOS as a thin remote that should *not* maintain its own slot (otherwise the same human's wrist + phone double-counts), and all three propose the same phasing: core + bindings first (verifiable on Linux via `cargo test`), then web and Android (the two shells with runtime verification on the dev host), then backend, then the CI-only platforms (Windows, three Apple targets, watchOS last and trivial). This is the repo's own "core first, then one atomic commit per shell" convention reflected back, which suggests all three models read and respected the existing convention rather than imposing their own.

### Areas of Divergence

The most interesting divergence is GPT-5.5's catch about **intent vs. confirmed playback**. Claude Opus 4.8 and Gemini 3.1 Pro both proposed gating accrual on `intent.is_playing() && !muted`, treating the intent flag as ground truth. GPT-5.5 traced the reducer further and found that `Play` sets intent to "Playing" immediately, but `PlatformPlaybackStarted` is the only signal that audio actually began — which means on a web browser that blocks autoplay, accrual would start the moment the user clicks Play and continue until the eventual `PlatformPlaybackError` arrives milliseconds or seconds later. The proposed fix (introduce an `audio_confirmed_playing: bool` flipped by `PlatformPlaybackStarted`/`Paused`/`Error`) is a small change with material correctness implications. **Recommendation: adopt GPT-5.5's gating.** The cost is one boolean and a handful of reducer arms; the benefit is that "listening time" actually means listening time across all six shells, including the ones with weaker autoplay guarantees.

The second meaningful divergence is **whether sync cadence belongs in core**. Opus says yes (emit `Effect::RequestSync` when threshold crosses, centralizing policy in core). GPT-5.5 says no (shells observe `unsyncedMs` and decide their own cadence based on lifecycle, reachability, and auth state — none of which the core knows about). Gemini sits in the middle (no explicit effect, but shells subtract acknowledged time via a command, which subtly conflates the G-Counter model). GPT-5.5's separation is more honest to the Clave kata: sync depends on knowledge the core deliberately doesn't have. **Recommendation: follow GPT-5.5 — don't emit a sync effect from core.** The cost is a tiny amount of duplicated "did we cross the threshold?" logic in each shell; the benefit is the core stays pure of network policy and each shell can implement platform-appropriate cadence (Android WorkManager, iOS BGTaskScheduler, web Service Worker, etc.).

The third divergence is around **what the sync wire carries and how acknowledgement works**. Opus and GPT-5.5 both commit fully to the G-Counter abstraction: the device's slot is absolute, the client always pushes the full counter, and acknowledgement only updates a display baseline — it never decrements local state. Gemini's design mixes paradigms: it nominally uses CRDT counters but asks the shell to subtract synced milliseconds from a local "unflushed" accumulator, which is the delta-sync mental model that *forced* CRDTs in the first place. **Recommendation: follow Opus/GPT-5.5 — never decrement, never ack-and-subtract.** This is the entire point of choosing G-Counter over deltas; the simplicity of the model collapses if you reintroduce delta-style state.

The fourth, and arguably most important, divergence is **the privacy posture**. GPT-5.5 was the only model to actually read Cascade's existing privacy page (`apps/web/public/privacy/index.html`) and discover that it currently promises *no accounts, no analytics, no servers receiving user data, no data-collection network calls*. Default-on tracking with a sync service breaks every one of those promises. Opus and Gemini both discussed default-on defensibility in the abstract and concluded the data minimization argument is enough; neither flagged that the current copy needs to change before the feature ships. **Recommendation: treat the privacy page update as a release gate.** GPT-5.5 is correct that the copy and the toggle must ship in the same artifact, otherwise existing users have been promised something the new release contradicts.

### Unique Insights Worth Noting

Two unique findings deserve to be folded into the final plan regardless of which model's overall architecture is adopted. First, **GPT-5.5's epoch / `device_id` rotation on deletion** is the only mention of a real correctness gap in G-Counter designs: monotonic counters and "delete my data" are in tension because a forgotten offline client can resurrect deleted totals by PUTing a higher stale counter days later. Rotating the local `device_id` when the user invokes deletion ensures stale offline writes hit a fresh slot (or no slot) rather than the deleted one. Second, **Opus's `elapsed_ms` clamping in the core** is the cleanest single mitigation for the highest-risk unknown all three models flagged (clock-jump inflation from sleep/wake gaps or malicious clocks). Capping per-tick deltas at ~5 s — since shells tick at 250 ms, any larger delta is by definition a gap rather than listening — neutralizes the largest single source of inflated counters without requiring server-side anomaly detection. Both of these are minor additions to whatever core API design ends up shipping.

### Recommendations

The composite, implementation-ready plan is:

1. **Core API:** follow Claude Opus 4.8's overall structure (separate `listening.rs`, new Commands/Effects/Snapshot fields, reducer integrates on the existing `Tick` arm) but adopt **GPT-5.5's `audio_confirmed_playing` gating** instead of `intent.is_playing()`, **don't emit a `RequestSync` effect from core** (let shells observe `unsyncedMs`), and **add Opus's per-tick `elapsed_ms` clamp** as cheap input sanitization.
2. **Persistence:** Opus's per-platform table verbatim, plus GPT-5.5's tighter local-persist threshold (~5 s) so a process kill loses at most 5 seconds.
3. **Backend:** Opus's three-table schema and four-route API, but use **GPT-5.5's opaque server-side session tokens** instead of JWTs so revocation is trivial.
4. **Sync:** pure G-Counter — absolute counters only, never decrement, never ack-and-subtract — with **GPT-5.5's `device_id` rotation on "delete listening data"** to close the resurrection loophole.
5. **Privacy:** treat the existing privacy page rewrite as a launch blocker (GPT-5.5's catch). The defensibility argument is data minimization (all three models), formalized as "we cannot reconstruct when you listened, only how much."
6. **Build order:** core → bindings → web → Android → backend → Windows (CI) → Apple (CI) → watchOS (CI, thinnest). Front-load the validation spike GPT-5.5 proposes (confirm `PlatformPlaybackStarted` reliability and untimed-tick battery cost on web + Android) before committing to the full design.

The riskiest unknown to validate first, by unanimous consent of all three models, is **clock integrity and tick coverage during background audio** — the merge math is bulletproof, but the input deltas the merge consumes are only as trustworthy as each shell's ability to tick reliably during background playback without inflating from sleep/wake gaps. Run that validation on web and Android before writing a line of backend code.
